## 1. The project in plain words

- A data pipeline is a chain of tables: raw tables -> cleaned table -> daily summary table. When a dashboard number
  suddenly looks wrong, engineers look at the **lineage map** (which table feeds which), see which upstream tables
  changed recently and GUESS the culprit. That guess is based on "these two things happened near each other". It is not proof.
- **LineageRCA** tests the guess. Lakehouse tables (Delta Lake / Apache Iceberg) keep every old version as an immutable
  **snapshot** ("time travel"). When a data-quality monitor fires, the harness: (1) walks the lineage graph backwards and
  shortlists upstream tables that changed shortly before the anomaly (the suspects); (2) for each suspect, RE-RUNS the
  downstream steps with that one table read at its pre-change snapshot (everything else pinned to what the anomalous
  run used); (3) compares the result. If the anomaly disappears, the suspect is **CONFIRMED** as a cause; if it stays,
  it is **DENIED**. This is a **counterfactual test**: "what would the output have been if this table had not changed?"
- Claim we test: replay-confirmation finds the true cause with higher precision than lineage correlation alone, on a
  multi-stage pipeline with injected faults. Narrow novelty: native lakehouse time travel as the replay mechanism, guided by
  lineage shortlisting, aimed at data-quality root causes. Replay in general is NOT new (BugDoc, Newt, aaiclick exist);
  never claim otherwise.
- Course context: this is our **BACKUP capstone idea** (the main idea is CascadeGuard, in a separate folder). We build a
  working demo in case we need it. Graded on: Problem Statement, Application Feasibility & Background Study,
  **Implementation**, Presentation & Viva (equal weight).
- **The demo = a real mini lakehouse pipeline on a laptop (Delta tables via `deltalake`, queries via DuckDB, NO Spark,
  NO Java, NO Docker) + injected faults with known ground truth + monitor + replay harness + baselines + a report.**
  The time travel and the re-execution are REAL. The data and the faults are SYNTHETIC. Say exactly that.

### 2.2 Honesty (this project is graded in a viva; fabricated results would be fatal)
- Everything generated by the pipeline and fault injectors is labelled **SYNTHETIC**: in plot titles, the HTML report
  header, console output and a `source=synthetic` column in CSVs.
- Never write a number into README, PROGRESS, docs or the report unless it came from a run you actually executed.
  Paste the real command and its real output into `build_logs.md`.
- We author BOTH the faults and the method, so the evaluation is partly circular. Say so in the report. Fix every
  threshold in `configs/` BEFORE looking at held-out scenarios; report held-out seeds (1-5) and the "boundary"
  scenarios (two causes, non-deterministic transform) SEPARATELY from the demo seed (42).
- Do NOT tune thresholds, data sizes or fault sizes until replay "wins". If a scenario does not behave as expected
  (for example replay gives a wrong verdict), keep it, and report it honestly in `build_logs.md` and in the report.
- A scenario where lineage-only already finds the cause (the fault is the most recent change) MUST be included, so the
  comparison is fair. Do not hide scenarios where the baselines tie or win.
- The baselines must be implemented in good faith (the best simple version we can defend), not as strawmen.
  Document exactly what each baseline does in `ARCHITECTURE.md`.
- Replay is only a clean counterfactual for PURE, DETERMINISTIC, BATCH transforms. State this limit in the report.

## 6. Coding standards

- Python 3.12 style, full type hints, pydantic v2 models, `pathlib` for paths (Windows-safe), UTF-8 everywhere.
- Deterministic: one seeded `numpy.random.Generator` passed explicitly; a LOGICAL clock for commit times (never the
  wall clock inside data or metadata); the same seed must give identical table contents (compare content hashes, test it).
- Compute cost is measured with `time.perf_counter()` only for reporting; it never influences a verdict.
- Small modules (aim for < 250 lines), small functions, plain-language comments and docstrings: four students
  must be able to explain every file in a viva. Prefer clarity over cleverness.
- No hidden globals, no `print` in library code (use `logging`; the demo may print tables via `rich`).
- Every verdict carries an explanation string (WHY: monitor value before, after replay, threshold) and the snapshot ids involved.
- Every new module gets at least one test. Tests must not need network, Docker or Java.
- Windows: pass Delta paths as `str(Path(...))`; never hard-code `/`; do not assume a shell.

1. `python scripts/check_env.py` prints all REQUIRED checks green (optional tools may be "missing").
2. `python demo/run_demo.py` finishes in under 120 s with no network and writes to `outputs/`: an HTML report, PNG figures
   per scenario, and CSV tables (snapshots, lineage edges, replay verdicts). Prints a summary table.

   s3 (fault is the latest change) shows replay and the lineage baselines all agreeing. s4 (control, no fault) raises
   no monitor alarm. s5 (two causes) and s6 (non-deterministic transform) report whatever actually happens, with the
   caveat in 2.2.
4. A summary table prints top-1 accuracy of replay vs the two baselines, false-confirm rate and compute cost, with held-out seeds separate.
5. `pytest -q` passes; `ruff check .` is clean.
6. README quick start works from a clean clone.
7. `docs/DEMO_SCRIPT.md` (3-minute talk track) and `docs/VIVA_NOTES.md` (likely questions, honest answers, known
   limitations) exist and quote only real numbers from `outputs/` / `results/`.
