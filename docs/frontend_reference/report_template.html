The usual question
Is each autoscaler healthy?

Each controller looks fine on its own metric, so nothing looks wrong until their actions collide.

The question we ask
Are the autoscalers fighting each other?

Read all three decisions on one timeline and flag opposing, alternating and cascading actions, with the reason.

Read this first

The simulator contains the controller behaviour we modelled (HPA, VPA, KEDA, Kafka rebalance). A conflict appears only if that modelled behaviour produces it. These results are a mechanism demonstration, not evidence that the same thing happens, or how often, on real clusters. We wrote both the scenarios and the detectors, so the held-out seeds below are a sanity check, not independent proof. All parameters are documented defaults or marked "assumption" in configs/controllers.yaml; none were tuned to make a conflict appear.

How detection runs

Five stages, no machine learning

01

Observe

Reads the decisions of HPA, VPA and KEDA plus the workload state. Here the data comes from the simulator; a read-only Kubernetes adapter exists but has only been tested on hand-made data.

02

Correlate

Groups decisions from different controllers that happen close together in time: who acted near whom.

03

Detect

Four deterministic detectors: opposing actions, alternating controllers, direction reversals and the restart, rebalance, scale-out cascade. Every flag carries a plain-language reason and the event ids behind it.

04

Arbitrate

A one-rule stub (VPA yields to HPA or KEDA during a scale event). Off by default and not used in any result on this page.

05

Report

Scores each run against ground truth written beforehand and writes this page, the CSV tables and the timelines.

Limitations

Limitations you should know

  • Simulated only: the model encodes our assumptions (see configs/controllers.yaml); results show a mechanism, not real-cluster frequency or magnitude.
  • Circularity: we author the conflicts and the detectors. Held-out seeds change only the random jitter, not the story; real-cluster scenarios are future work.
  • In-place pod resize (GA in Kubernetes 1.35) may remove the VPA restart in practice; scenario s5 reports what our model does, nothing more.
  • Two controllers acting on one replica count overwrite each other in the simulator (last writer wins). On a real cluster that is a misconfiguration: Kubernetes does not coordinate two autoscalers on one target, and as we understand it (not verified here) KEDA's own admission check is meant to block it for its targets. So s2 is a deliberately forced setup, not a common one.
  • Kafka rebalances are logged whenever the set of ready pods changes, even in scenarios with no Kafka traffic (s1, s4). Those orange bands are a modelling artefact; with no lag and no KEDA they do not affect any detector result.
  • Detection latency is the firing time minus a hand-written truth start: the detectors are reactive, and predicting a conflict before it happens (the proposal's longer-term goal) is not attempted here.
  • Parameters marked "assumption" need validation on a real cluster.
