The old question
Which upstream table changed most recently?

A guess. Two things happened near each other; nothing was re-run to check.

The new question
If this table had not changed, would the problem still happen?

A test. Roll the suspect back to its earlier snapshot, re-run the downstream steps, and look.

Read this first

The data and the injected faults are SYNTHETIC and written by us. The time travel (Delta Lake snapshots) and the re-execution (DuckDB) are real. We wrote the faults, the decoys and the method, so the evaluation is partly circular: it shows that the mechanism works for pure, deterministic batch transforms on a five-table toy pipeline, not how often it works on real pipelines. Held-out seeds change the random data, not the types of fault. Thresholds are fixed in configs/ before the held-out run. Where results are awkward (s2, s5, s6, ties with the baselines) they are shown below as they came out.

How a replay runs

Five stages, no machine learning

01

Pipeline and snapshots

Delta tables on local disk; every commit is an immutable snapshot that can be read later. Synthetic orders, customers and exchange rates flow through two pure steps: clean, then daily revenue.

02

Lineage capture

One event per run records which snapshot of each input it read and which code version it used. That is what lets a replay pin everything except the suspect.

03

Monitor

Compares one day with the median of the previous days: row count, revenue and null rates. Plain thresholds, fixed in configs/ before the held-out run.

04

Replay harness

For each suspect: read it at the snapshot before its change, pin every other input and the code version, re-run only the steps downstream, repeat, then check whether the alarming metric is back inside the threshold.

05

Verdict report

CONFIRMED, DENIED, PARTIAL or INCONCLUSIVE per suspect, with the reason and the snapshot ids. Ground truth is read only afterwards, to score the verdicts.
